Current state

What is built and running

This repo holds the pre-save landing page for Blake Richardson's next release. What is actually built is a one-file placeholder: a black page with the artist name, one line of copy, and a green pre-save button that links out to his Fan Engage Pro profile on Render. Nothing else on the page is interactive. The full page described in RELEASE_PIPELINE.md (DSP buttons for Spotify, Apple, Amazon, and YouTube Music, email capture, social share) was never built.

Stack

  • Static HTML in public/index.html (about 1.4 KB). No framework, no build step. package.json has placeholder dev and build scripts and pins Node 18.
  • One serverless function, api/index.js, returns {status: "ok", timestamp}. It only runs on Vercel, not on GitHub Pages.
  • Two deploy paths are configured and they conflict. vercel.json sets framework vanilla with output directory public. .github/workflows/deploy.yml publishes public/ to GitHub Pages on every push to main, and public/CNAME claims presave.blakerichardson.com for GitHub Pages.
  • Load testing: k6 scripts in tests/load/ and scripts/run-load-test.sh, pointed at the Render staging app, not at this page.
  • Monitoring: monitoring-config.json describes two Better Uptime monitors on fanengage-pro.onrender.com with a Slack alert to #blakerichardson-presave. Documented only, never created.

Repo contamination

  • README.md, intake-router.js, and .env.example belong to a different project, the ClickUp Intake Router (Phase 1). The README does not mention the presave page at all.
  • intake-router.js imports axios and dotenv, which are not in package.json. It cannot run from this repo and should not be treated as part of the app.
  • This diverges from the house playbook (Next.js 16 plus Supabase plus Vercel). That is fine for a one-page campaign site, but the next agent should not "fix" the stack without a decision.

Workflow

How to make a change safely

Critical rules

Pick one deploy target before touching DNS. Today the workflow deploys to GitHub Pages and vercel.json expects Vercel, and the subdomain points at neither. Do not add a third path.

Keep the button pointing at the Fan Engage Pro profile unless Kevin says otherwise. That link is the only thing on the page that works, and the FEP rewards schema already has a presave point source waiting for it.

Do not run intake-router.js or add its env vars. It is not this app.

  1. Pull main and confirm you are on 02b6240 or later. The tree should be clean.
  2. Edit public/index.html directly. Open it in a browser from disk to preview. There is no dev server.
  3. If the change adds an endpoint, put it under api/ and remember it only works on Vercel.
  4. Commit with a conventional message. Push to main. The GitHub Pages workflow runs on push.
  5. Smoke test the page at whichever address is live. Click the button and confirm the FEP profile loads.
  6. Update RELEASE_PIPELINE.md if the scope changed, and do not close JGF-1825 until the real page exists.

Conventions

House rules for this codebase

  • No env vars are needed for the page itself. The 17 names in .env.example (CLICKUP_API_KEY, INTAKE_LIST_ID, SLACK_WEBHOOK_URL, the W1 to W6 list ids, and the field ids) belong to the intake router, not to this app. Ignore them.
  • The one monitoring placeholder is SLACK_WEBHOOK_BLAKERICHARDSON_PRESAVE in monitoring-config.json. Its value lives only in Better Uptime once that is set up.
  • Task ids: JGF-1828 (infrastructure and DNS), JGF-1842 (uptime monitoring), JGF-1825 (page build and launch), JGF-1843 and JGF-2353 (load test). Reference them in commits.
  • Commits are short imperative sentences. Six of the twelve were co-authored by Claude. Keep em dashes out of commit messages and page copy; the current page title contains one.
  • Docs live at the repo root as Markdown. Add new ones there, and fix README.md so it describes this app.
